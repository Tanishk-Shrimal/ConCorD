Inside ConCorD

Overview

The big picture

ConCorD works in two separate phases. Compiling turns your operators into a plan: everything that can be decided without data, from Wick contractions to memory layout. Running reads the lattice data and follows the plan. Steps 2 to 7 of this guide happen while compiling, step 8 while running.

Step 1

What you give ConCorD

You give ConCorD two files. One describes the physics. The other gives the settings and says where the data are.

operators.py: the physics

A short Python file with one function, called build by default, that returns the correlators you want. A complete example for the pion:

from concord_lqcd.core import Correlator, Operator, dbar, gamma5, u

def build():
    # d̄ γ5 u at one point "x"
    pion = Operator(dbar("x", "color", "s1") * gamma5("s1", "s2") * u("x", "color", "s2"))
    return {"pion": Correlator(pion, pion.dagger())}
Quark fields
u, d, s, c, b (also l, a generic light quark, and t) and the barred versions. Each takes three labels: a position label, a color index name and a spin index name.
Spin and color tensors
γ matrices such as gamma5, named spin matrices such as Cg5, and epsilon for baryons.
Displaced quarks and helpers
transport, derivative and shift move a quark along a path. build_baryon_operator builds a standard baryon in one line.

Three rules cover how these pieces combine:

  • A repeated index name is summed over. In the pion, color appears twice, so the colors are contracted; s1 and s2 join the spins through γ5.
  • Quarks with the same position label sit at the same point and share one momentum. One label gives a single hadron; two labels, such as "x" and "y", give a two-hadron operator like Nπ or ππ. Momenta are given per label.
  • Operators can be added and multiplied by numbers. Isospin combinations such as (π⁺π⁻ + π⁻π⁺ + π⁰π⁰)/√3 are written exactly like that.

The function returns a Correlator(sink, source), a three-point Correlator(sink, current, source), a whole CorrMatrix of operators, or a dictionary of named correlators. The file contains no run settings: no times, no N_v, no data.

job.yaml: settings and data

Two short sections label the file: schema_version (always 1) and job, a name that is stored in the plan and in the results. The other sections fall into two groups. The first group decides the plan. The second is only read when running.

Why the split matters
  • You compile once and run many times, for every configuration and source time, with the same plan.
  • You can see the cost before you have any data.
  • Changing N_v, the spin basis or the contraction order needs a new plan. Changing configurations, times, the lattice size, workers or the device does not.
Step 2

From operators to Wick terms

ConCorD first works out which quark connects to which. This is pure bookkeeping: no N_v and no data are involved yet. It happens in four small steps.

2a. Multiply out the sums

An operator can be a sum. The ππ operator with I = 0 is (π⁺π⁻ + π⁻π⁺ + π⁰π⁰)/√3, and π⁰ is itself (ūγ5u − d̄γ5d)/√2. ConCorD multiplies everything out, so each matrix entry becomes a weighted sum of basis correlators, in which every operator is a single product of quark fields. Identical products are combined and products with zero weight are dropped. Operators are also written in one standard form, so two operators that mean the same thing look the same.

For the ππ matrix with 5 operators, the 25 entries turn into 676 basis correlators.

2b. Pair the quarks

For each basis correlator, ConCorD pairs every quark with an antiquark of the same flavor, in every possible way. Each pairing is one Wick term. Each pair becomes a propagator, and each term gets a sign from the order of the quark fields.

The number of terms follows from counting the ways to pair: for each flavor, (number of quarks of that flavor)!, multiplied over the flavors.

CorrelatorQuarks per flavorWick terms
π⁺ to π⁺u: 1, d: 11
proton to protonu: 2, d: 12! = 2
pp to ppu: 4, d: 24! × 2! = 48
tritonu: 4, d: 54! × 5! = 2,880
⁴Heu: 6, d: 66! × 6! = 518,400

u and d are always different flavors here, even when they use the same perambulator. The pairing never assumes isospin; isospin enters only through the weights you wrote in the operators.

Worked example: the NN matrix

The two-nucleon ¹S₀ basis has 17 operators. Each one is two protons with back-to-back momenta, p and −p, coupled with Cγ5. Swapping p and −p gives the same operator, so there is one operator per pair {p, −p}. For |p|² up to 4 (in units of 2π/L) that is 1 + 3 + 6 + 4 + 3 = 17.

A correlation matrix uses every operator once as the sink and once as the source, so it has 17 × 17 entries. Each entry pairs the 6 quarks of the sink (u u d u u d) with the 6 antiquarks of the source.

Entries: 17 sink operators × 17 source operators289
Terms per entry: 4 u quarks (4! ways) × 2 d quarks (2! ways)48
Wick terms in the matrix289 × 48 = 13,872

The deuteron channel ³S₁ uses (pn − np)/√2, a sum of two products. Each entry therefore has 2 × 2 = 4 basis correlators, each with 3! × 3! = 36 terms. That gives 144 terms per entry and 289 × 144 = 41,616 for the matrix.

2c. Contract each basis correlator once

ConCorD remembers every basis correlator it has contracted. If exactly the same one turns up again (same operators, same momenta), its Wick terms are reused. In practice this rarely happens within one matrix, because every entry carries its own momenta: in the ππ, Nπ and NN matrices we tested, every basis correlator was different. The sharing that matters for the cost comes later, in step 4.

2d. Write each term as quark lines

Each Wick term is then stored as one record, which the code calls the Physics IR. It holds:

  • The quark lines. Each line has a quark end and an antiquark end. Each end records which operator, position, color and spin index it belongs to, any transport or derivative applied there, and whether that end is smeared (distillation) or a point.
  • The spin and color tensors (γ matrices, Cγ5, ε) and any gauge links, which tie the quarks of one hadron together.
  • The momentum of each position label.
  • One number: the weight from step 2a times the sign from step 2b.

So each record is a small graph of how the quarks connect: the quark fields are the points, the quark lines and the spin and color tensors join them. The NN ¹S₀ matrix gives 13,872 such records.

These records exist only while compiling. The plan file does not keep them; it keeps the result of the next steps, which is much more compact.

Still to come for these terms

Some Wick terms turn out to be identical apart from their sign, and cancel. ConCorD only finds that in step 4, when it compares everything across the whole matrix. Step 3 first turns each record into tensors that can actually be computed: perambulators, distillation kernels and spin matrices.

Step 3

From Wick terms to tensor networks

Step 2 said which quark connects to which. Step 3 says what to multiply. Each Wick term becomes a small tensor network: a few numerical arrays joined by shared indices. This is where distillation, the eigenvectors and N_v come in.

Why distillation splits the work this way

In distillation every quark field is smeared with V V†, where V holds the N_v Laplacian eigenvectors on one time slice. V acts on color and space but never on spin. That suggests a natural split into three kinds of pieces:

  • the color and space sums of each hadron, done once per time slice;
  • the propagation of each quark from one time to another;
  • the spin structure, which is just small 4 × 4 matrices.

Things to notice

  • No times appear in the network. A perambulator is "from the source operator to the sink operator", not "from time 0 to time 12". The times are filled in when running, so one network serves every source and sink time.
  • Loops need perambulators from a time slice back to itself. A loop at time t uses τ(t, t), so loop terms need perambulators from every time slice, not only from the source.
  • Trivial blocks are removed. A meson block with no momentum and no displacement is V†V, which is the unit matrix when the eigenvectors are orthonormal. When you declare that (the built-in eigenvector reader does), ConCorD drops the block and joins its two lines.
  • Point currents in three-point functions are folded into generalized perambulators that you supply, so they do not appear as separate blocks.
Still to come for these networks

Across a whole matrix, many of these networks are identical, or share identical pieces. Step 4 cuts each Wick term's graph into its connected parts and keeps each distinct part only once. That collection is the DAG.

Step 4

Sharing across the whole matrix: the DAG

After step 3, every Wick term has its own private network. Many of them are the same, or are built from the same parts. Step 4 finds this and stores each thing once. The result is a DAG.

What a DAG is

DAG stands for directed acyclic graph. Arrows run from what is needed to what uses it, and nothing depends on itself. Unlike a tree, a node may feed several users. That is exactly what sharing looks like: one network computed once, used by several terms.

Three kinds of sharing

  • Input tensors. Every perambulator, block and spin matrix is stored once, however often it is used. There is one perambulator per flavor; which time slices it connects follows from where it sits in a network.
  • Networks. Each Wick term's graph is cut into its connected parts. Two parts count as the same when they use the same inputs, connected in the same way, at the same operators, whatever the index names. Each distinct part is stored once.
  • Whole terms. Within one correlator, terms made of the same networks are added together. If their coefficients cancel exactly, the term disappears. This is where cancellation happens.

Mesons with loops share a lot: the same loop at one time slice appears in many terms. The NN matrix shares nothing at this level. Each of its terms is one connected network, and all 13,872 differ in momenta or wiring. They still contain identical parts, such as the same two baryon blocks joined by the same perambulator, but finding those needs a contraction order. That is step 5.

What the plan keeps

This DAG replaces the per-term records of step 2. The plan file stores the distinct inputs, the distinct networks, and for every correlator the list of terms: a coefficient times a product of networks.

Optional: merging terms that give the same numbers

Some terms are different networks but give the same numbers, and the comparison above cannot see it. In baryon systems, terms can be related by the antisymmetry of the blocks or by identities between spin matrices. And u and d are different flavors in all of the above, so Lu(t) and Ld(t) are different networks even when they use the same perambulator data. If you switch on Wick merging (compile.wick_aggregation.enabled: true), ConCorD proves such equalities exactly and merges the terms right after this step. Declaring u and d numerically equal (compile.numerical_flavor_groups: [[u, d]]) lets it merge the u and d terms too; ConCorD accepts this only if both flavors read the same perambulator files. For NN ¹S₀ with one operator, merging alone turns 48 terms into 16. For the 18-operator ππ matrix, merging with u = d cuts the number of distinct contraction steps (step 5) by 8.6 times. It is off by default.

Step 5

Contraction order and shared partial products

Each network from step 4 is still one large multiplication of up to 32 tensors (10 for one proton, 22 for two nucleons, 32 for three). It is computed as a sequence of pairwise steps: multiply two tensors, sum over the indices they share, keep the result, repeat. A network of n tensors takes n − 1 steps. This step has two parts: choosing the order of the steps in each network, and then finding the steps that several networks have in common.

5a. What one step costs

A step costs one multiply and one add for every combination of values of all the indices involved, summed or not. What it keeps is one number for every combination of the indices that stay open. An eigenvector index has N_v values (32 in all the examples here), a spin index 4. So every eigenvector index left open multiplies both the memory and the cost of the next steps by 32.

Spin matrix × perambulator: indices 4, 4, 32, 32, 42 × 65,536 = 1.3 × 10⁵
Baryon block × (spin matrix · perambulator): indices 32, 32, 32, 32, 4, 42 × 1.7 × 10⁷ = 3.4 × 10⁷

These are the compiler's own estimates. Real complex arithmetic takes about four times more operations, the same factor for every order, so the comparisons below are not affected. All numbers on this page are for one time slice.

The exact order is a single chain: each step adds one more of the original tensors, and it never holds more than five open indices (three eigenvector, two spin). The greedy order joins the d perambulator to the sink side by summing only one index, which leaves seven open: three eigenvector and four spin indices, 8.4 million numbers, 134 MB in double precision. That step and the next each run over four eigenvector and four spin indices at once, 5.4 × 10⁸ each, so this network costs 16 times more than it needs to.

Greedy did not have to do this, even by its own rule. At its step 7, joining B̄(0) to either of the two spin-and-perambulator products would have grown memory by 0.48 million numbers, against 7.8 million for the pair it took. To stay fast it keeps only one candidate partner for each tensor, and those partners had already been used. On the other proton network greedy is fine: 2.0 × 10⁸, the same as the exact order. So how well greedy does depends on the shape of each network, not only on its size. A bad order also costs memory: for the whole proton correlator the greedy plan needs 154 MB of buffers, the exact one 18 MB.

5c. The methods

ConCorD chooses an order for each distinct network on its own, using the opt_einsum library. You pick the method with compile.contraction.strategy:

  • greedy (default): one fast pass, as above. Always the same result for the same input.
  • auto: an exact search up to 4 tensors, short branching searches up to 14, greedy above. For NN and anything larger it is greedy.
  • dynamic-programming: the exact cheapest order of each network (strictly, among orders that only ever join tensors sharing an index). The search time grows quickly with the number of tensors.
  • auto-hq: exact up to 16 tensors. Above 16 it keeps the best of 128 randomized greedy runs. Every compile finds the same cost per network, but several orders can tie at that cost, and which one comes back depends on Python's string hashing, which changes from process to process. The tied orders share steps differently (5d), so for NN ¹S₀ with one operator the whole plan came out between 1.4 and 2.0 × 10¹⁰ FLOPs in our compiles. Setting PYTHONHASHSEED makes it repeatable. A run always uses the saved plan, so the results are not affected.
  • reuse-aware: builds the whole plan four times, with greedy, dynamic-programming and two branching searches, using one method for every network each time. Each version is taken through sharing (5d), scheduling and buffers (step 6), and the one with the fewest FLOPs is kept, as long as it needs no more memory than the greedy plan, or than your memory limit. If any network has more than 12 tensors, it builds only the greedy version.
  • adaptive: saves the greedy plan. When a run starts, it also builds the reuse-aware plan from the same DAG, times both on made-up data on the run's device, remembers the timing for later runs, and uses the faster plan. If the two plans are the same, there is nothing to time.

5d. When two steps are the same

Once every network has its order, ConCorD compares every step across all networks. Two steps count as the same when:

  • their two inputs are the same. For a tensor that means the same data in the same place: the same block or spin matrix at the same end (sink or source), or the same perambulator between the same two ends, in a correlator with the same number of operators. An input that is itself the result of an earlier step must be the same step.
  • the inputs are wired the same way: the same legs are summed and the same legs stay open. The internal names of the indices do not matter, and neither does which input comes first.

The comparison is about how a step is built, never about its numbers. Two steps that give equal numbers for a physics reason, a symmetry for example, are still done twice. And because an input can be an earlier step, a step can only be shared if everything below it is shared too. What two networks share is always a piece built from the bottom up, the same inputs joined in the same way, though not necessarily the first steps of each order.

Each distinct step is done once, and its result goes to every network that needs it. The steps and the values passed between them form a second DAG, finer than the one in step 4. What this finds in real matrices, with the greedy order:

5e. Rows and columns: where the sharing comes from

Every network of a matrix element Cij joins two halves through perambulators. The sink half belongs to operator i: its block at time t and its spin matrices. The source half belongs to operator j, at time 0. The perambulators are the same for the whole matrix. So where a step can be reused depends on which halves it contains.

Counting the distinct steps by who uses them, for the proton with 7 operators (one local, six displaced) and for ππ with 5 operators:

In the proton all the useful sharing is one-sided. Greedy happens to build the expensive half from the sink block, so those products are made once per row and used by all 7 correlators in it. auto-hq builds from the source block and reuses along columns. A step that contains both blocks is never shared, not even between the two networks of one correlator.

A matrix of n operators has n rows but n² elements. As the matrix grows, the one-sided work grows like n and the joining work like n², so the joining steps decide the cost. Here auto-hq's joining steps cost 16 times less than greedy's (1.75 × 10⁹ against 2.8 × 10¹⁰). That, more than the sharing, is why it wins for baryons.

Mesons share more ways. A ππ matrix element has many Wick terms, and their networks have steps in common. Row and column sharing cuts the one-sided work from 5.2 × 10⁹ to 3.2 × 10⁸. Most of what remains, 3.6 × 10⁹ of 4.9 × 10⁹, is in steps that only one network uses.

5f. Why the order and the sharing interact

The order of each network is chosen without looking at the others, and the sharing is found afterwards; it never changes an order. So the cheapest order for each network does not always give the cheapest plan. FLOPs after sharing, per time slice:

For baryons auto-hq wins by 2 to 10 times, because, as in 5b, greedy sometimes leaves far too many indices open. For mesons it goes the other way. In ππ with 2 operators, greedy's orders are a little worse network by network (2.0 × 10⁸ against 1.8 × 10⁸ before sharing), but they share more, and after sharing auto-hq's plan needs 21% more FLOPs; with 5 operators, 32% more. reuse-aware exists to catch exactly this, but it only searches when every network has at most 12 tensors. For ππ with momenta, NN and anything larger it is the same as greedy.

Two things ConCorD does not do: it never changes a network's order to create more sharing, and reuse-aware uses one method for all networks instead of mixing them.

What to choose

Baryons: auto-hq. In these examples it needs 2 to 10 times fewer FLOPs than greedy, and less memory. Mesons: greedy, or reuse-aware, which makes the comparison for you when the networks are small. To compare two methods on your own matrix, compile it with each and read both plans with concord inspect (step 7).

Still to come for these steps

The distinct steps describe one time slice, and nothing yet says in which order they run or where their results are kept. Step 6 puts them in an order of execution and decides when each result can be freed and which memory it goes into.

Step 6

Scheduling and memory

After step 5 ConCorD knows what to compute. Step 6 decides in which order and where each result is kept, so that the memory a run needs is known before it starts.

6a. The complete to-do list

Everything left to do is written as one more DAG, with four kinds of operations:

  • Get an input: read a perambulator, build a baryon or meson block, take a spin matrix.
  • Do a contraction step from step 5.
  • Form a Wick term: its coefficient times the product of its network results.
  • Add the terms into each requested correlator.

This DAG says only what depends on what. Because N_v is known, the size of every value in it is known exactly. For the proton at N_v = 32 the largest is a 134 MB intermediate (N_v³ × 4⁴ complex numbers) made by the greedy order. No schedule can make a single value smaller; only the contraction order of step 5 can.

6b. The order of execution

ConCorD turns the DAG into one list, a schedule. With the default strategy, memory_aware, it repeatedly looks at the steps whose inputs are ready and runs the one that frees the most memory: the one whose inputs have no other use left, minus the size of the result it creates. The alternatives are critical_path and topological.

The schedule gives every value a lifetime, from the step that makes it to the last step that uses it. After that it can be freed. The requested correlators are kept to the end.

6c. Buffers

Values whose lifetimes do not overlap can share the same piece of memory, a buffer. With the default, best_fit, each new value goes into the smallest free buffer that is big enough; if none is free, a new buffer is made. If that leaves too much unused space, ConCorD also tries packing all lifetimes at once and keeps the smaller result. The buffers together are the plan's memory requirement. You can set a hard limit (compile.physical.memory_limit_bytes); if the plan cannot fit, compiling fails with the smallest size it found.

The plan is now complete

Everything that can be decided without data has been decided: the inputs, the distinct steps, their order, every value's size and buffer, and the total memory, all for one time slice. Running several time slices at once multiplies the memory by that number; that choice is made when running, in step 8. Step 7 is about what is saved in the plan file and what concord inspect shows from it.

Step 7

The plan file and concord inspect

Everything decided in steps 2 to 6 is saved in one file, the plan, with the ending .concord. It describes the whole computation for one time slice and does not depend on the data, the lattice size, the times or the machine.

plan.jsonThe plan itself: the DAG of step 4, the orders and shared steps of step 5, and the to-do list, sizes, schedule and buffers of step 6, with the compile settings and, if Wick merging is on, its proof.

The plan of the proton example in examples/proton/, compiled with N_v = 64, is 191 kB of text, 16 kB compressed. Large matrices give large plans: the 14-operator Nπ plan at N_v = 32 is 270 MB of text.

Three checks each time a plan is used

  • Is the file intact? The fingerprint of plan.json must match the one in the manifest. A damaged or hand-edited file is refused.
  • Was it made for this job? ConCorD recomputes the fingerprints from your current operators file, its local helper files, the function name, the parameters and the compile settings (including whether the built-in eigenvector reader is used), and checks that the plan was made under the same compiler rules, a version number stored in the manifest. If any of them changed since compiling, the plan is stale and ConCorD asks you to recompile. Changing data paths, configurations, times, the lattice size or the device never makes a plan stale.
  • Is it consistent? The plan's internal records are checked against each other before running.

concord inspect has no job file, so it makes only the first and third checks.

Step 8

The run: data, blocks, contraction

concord run takes the plan and the data and fills in the numbers. The work is a grid of work units: one gauge configuration with one set of operator times. For example, 10 configurations with one source time and 64 sink times make 640 work units. Every work unit is exactly the plan of step 6, with different data.

8a. Before any contraction

  • Load and check the plan, as in step 7. If the plan file does not exist yet, concord run compiles it first. A stale plan is refused unless you pass --replan.
  • Choose the device: the one named in the job file, the CPU by default. With device: auto, ConCorD takes a GPU if the plan fits in its memory. If not, it can still use the GPU, keeping the values in the node's memory and contracting them on the GPU in pieces. Only if that is not possible either does it use the CPU.
  • Choose how many time slices to run together (the time batch). By default ConCorD times a few batch sizes on made-up data and keeps the fastest that fits. Memory grows with the batch size.
  • Choose workers and threads. By default this follows from the plan: one thread per worker when the fixed cost per step dominates, as for two-meson matrices at N_v = 32; four when the arithmetic dominates, as for baryons. If fewer workers can start than the cores allow, they share the spare cores. There are never more workers than work units or than fit in memory, and small jobs run in one process. A worker needs some memory beyond its plan's buffers. When a rough allowance for it, 3 GiB per worker, does not fit all the workers, fewer workers first run one work unit each and measure what they use, and the remaining work units are split again from that measurement.
  • Open the output file and skip every work unit already marked done, so a stopped run continues where it left off.

8b. For each configuration

Running B time slices together gives every tensor an extra index for the time slice. That index is never summed over, so different time slices never mix; they only share each step's fixed cost.

8c. Workers

On a CPU node the pending work units are split over several worker processes. The parent process loads the plan once and the workers share it, so memory is not spent on many copies. Only the parent writes the output file. Measured with ConCorD 1.0 on one 64-core node at N_v = 32, for one configuration, one source time t0 and the 63 sink times t ≠ t0, the automatic choice ran:

8d. The output file

In results.h5What it holds
correlators/…/valuesOne array per correlator: configuration × time setting × the correlator's open indices, for example 4 × 4 for a proton with open spin.
completedA done flag for every work unit.
metadataThe job name, the plan's manifest, the run, lattice and data settings, the grid of configurations and times, and one fingerprint of the plan, the lattice, the grid and the data settings (file names and layout, not the file contents).

By default a second run on the same output file resumes. It refuses if the plan, the data settings, the lattice or the grid changed, because that would mix different calculations in one file. With --run-record or --report, a run also records where its time went: loading the plan, managing the output file, choosing settings, reading and building inputs, waiting for inputs, contracting, writing, and the rest. The terminal shows the total time.

Recap

The whole path

  1. Input. Operators in Python, settings and data locations in a job file.
  2. Wick terms. Sums are multiplied out and every quark is paired with an antiquark of the same flavor, with signs.
  3. Tensor networks. Each term becomes blocks, perambulators and spin matrices joined by indices.
  4. The DAG. Identical inputs, connected networks and whole terms are kept once; cancelling terms disappear.
  5. Steps. Each network gets a pairwise order; identical steps across networks are done once, and a step that uses only one half of a network serves a whole row or column of the matrix.
  6. Schedule and memory. The steps get a running order, every value a lifetime and a buffer, and the plan a memory figure.
  7. The plan file. All of this is saved, fingerprinted and readable with concord inspect before any data exist.
  8. The run. Blocks are built from the eigenvectors, perambulators are read, and the schedule runs on batches of time slices across workers, writing and marking each result.

This guide describes ConCorD 1.0.0. The example matrices are the operator bases of the performance study in the ConCorD paper (two-pion, nucleon-pion, two-nucleon and bb ū d̄ systems, and the triton); the counts, costs and memory sizes on this page come from running ConCorD's compile stages on those sets, and the times were measured on one 64-core CPU node. They illustrate the scale and will differ for other operators and machines.
